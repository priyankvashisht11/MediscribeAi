SPRINT 8 SPEC — Clinical Document Suite & Practice Analytics
============================================================

Product:    MediScribe
Sprint:     8 of N
Depends on: Sprint 7 complete (Deepgram live, SOAP PDF working, ICD-10 lookup,
            transcript persistence to PostgreSQL, full audit log, production
            deployment live on Vercel + Fly.io + Supabase + Upstash)
Goal:       Turn MediScribe from a note-taker into a document engine. By end of
            sprint, a doctor can end a session and download three documents in
            one click: SOAP note PDF (already exists), prescription PDF (new),
            and patient take-home instructions sheet (new). Additionally, a
            Practice Analytics page gives the doctor visibility into their OPD
            patterns — built entirely from data already in the DB with zero new
            AI calls. A lightweight PIN-based access gate is added to protect the
            live production URL before sharing with design partner clinics.

S8-0 — PIN-based Access Gate (new — required before design partner sharing)
---------------------------------------------------------------------------

Context:
  The app is live at mediscribe-ai-eight.vercel.app with no authentication.
  Before sharing the URL with pilot clinics, a minimal gate is needed to
  prevent random public access. Full auth (JWT, user accounts, clinic
  multi-tenancy) is Sprint 9. This sprint delivers the smallest viable gate:
  a single shared PIN stored in environment config.

  This is NOT a security system. It is an access deterrent to prevent accidental
  public use during the pilot period. Do not over-engineer it.

Backend:
  File: backend/app/config.py
    Add: access_pin: str = ""   (empty string = gate disabled, backward-compatible)

  File: backend/app/routers/auth.py  (new file)
    POST /api/auth/verify-pin
    Body: { "pin": "1234" }
    Returns: { "token": "<signed JWT>", "expires_in": 86400 }
      - Sign with settings.secret_key, HS256, 24h expiry
      - If access_pin is empty (""), accept any pin and return token
        (allows disabling the gate without code changes)
    Returns 401 if pin is wrong.

  File: backend/app/main.py
    Register: app.include_router(auth.router, prefix="/api/auth", tags=["Auth"])
    Add JWT verification middleware OR a FastAPI dependency `require_auth`:
      - Read Authorization: Bearer <token> header
      - Verify signature + expiry
      - Apply to ALL routers EXCEPT /health and /api/auth/verify-pin
      - If token missing/invalid → 401

  Set secret on Fly.io:
    flyctl secrets set ACCESS_PIN="your_4_digit_pin" --app mediscribe-api

Frontend:
  File: frontend/src/pages/PinGate.jsx  (new file)
    - Shown when no valid token in localStorage
    - Simple centered card: MediScribe logo + 4-digit PIN input + "Enter" button
    - On submit: POST /api/auth/verify-pin
    - On success: store token in localStorage("mediscribe_token"), redirect to /
    - On failure: shake animation + "Incorrect PIN"

  File: frontend/src/utils/apiFetch.js  (update)
    Add Authorization header to all requests:
      const token = localStorage.getItem('mediscribe_token')
      if (token) headers['Authorization'] = `Bearer ${token}`
    If any response is 401: clear localStorage, redirect to /login

  File: frontend/src/services/api.js  (update)
    Same — add Authorization header to axios instance via interceptor.

  File: frontend/src/App.jsx  (update)
    Add /login route → <PinGate />
    Wrap all other routes with a RequireAuth component that checks localStorage
    token expiry before rendering.

  Fly.io deploy after S8-0 backend:
    cd mediscribe/backend && flyctl deploy --remote-only

S8-1 — Prescription PDF Generation (backend)
---------------------------------------------

File: backend/app/services/prescription_generator.py  (new file)

The ClinicalNote model already has `medications` and `plan` text fields
populated by the LLM. Parse them into structured rows and render a PDF.

IMPORTANT — shared extraction function:
  Define `extract_medications()` as a standalone async function. It is imported
  and reused by instructions_generator.py (S8-3) so only ONE LLM call is made
  per session when a doctor downloads both documents.

  async def extract_medications(note: dict) -> PrescriptionExtraction:
      """
      Parses note["medications"] + note["plan"] into structured data.
      Called by both generate_prescription_pdf() and generate_instructions_pdf().
      """

New Pydantic schema:

  class MedicationItem(BaseModel):
      drug_name: str         # "Tab Amlodipine"
      dose: str              # "10mg"
      frequency: str         # "Once daily (OD)"
      duration: str          # "30 days" or "Ongoing" or "As needed"
      instructions: str      # "Take after food" or ""

  class PrescriptionExtraction(BaseModel):
      medications: list[MedicationItem]
      special_instructions: str
      investigations: list[str]
      follow_up: str

Prompt to Perplexity (same client setup as note_generator.py):

  system: "You are a medical scribe. Extract structured prescription data from
           the clinical note text provided. Return valid JSON only."
  user:   "Plan section: {plan}\nMedications field: {medications}\n
           Extract all prescribed medications with dose/frequency/duration.
           Also extract any investigations ordered and follow-up timing."

PDF layout (fpdf2 — same teal PRIMARY colour, Helvetica, as existing pdf_generator.py):

  ┌─────────────────────────────────────────────────────┐
  │ MediScribe                    Prescription | Date   │  ← header bar (teal)

  │ Dermatology                   Date: 13 May 2026     │

  │ Rx                                                  │

  │     Take after food                                  │
  │  2. Tab Paracetamol 500mg    TID       5 days       │
  ├─────────────────────────────────────────────────────┤
  │ INVESTIGATIONS ADVISED                              │
  │  - ECG                                              │
  ├─────────────────────────────────────────────────────┤
  │ Special Instructions: Salt restriction <2g/day      │
  │ Follow-up: 2 weeks                                  │

Function signature:
  async def generate_prescription_pdf(
      note: dict, session: dict, doctor_name: str,
      patient_name: str = "Unknown",
      patient_age: int | None = None,
      patient_gender: str | None = None,

Error handling: if extract_medications() fails or returns empty medications,
fall back to rendering raw note["medications"] as a text block. Never raise.

S8-3 — Patient Instructions Sheet PDF (backend)
-------------------------------------------------

File: backend/app/services/instructions_generator.py  (new file)

Plain-language take-home sheet. NOT clinical language. A patient who saw
the doctor for 4 minutes walks out with a sheet they can actually read.

IMPORTANT — reuse extract_medications from S8-1:
  from app.services.prescription_generator import extract_medications
  Do NOT make a second LLM call for medications.

Content sources:
  - Condition summary:  One short LLM call to simplify note["assessment"]
                        into 2 plain-English sentences (see prompt below).
  - Medications:        Reuse extract_medications(note) result.
  - Warning signs:      Extracted from note["plan"] — sentences containing
                        "emergency", "immediately", "if worsening", "chest pain",
                        "come back if".
  - Tests ordered:      investigations list from PrescriptionExtraction.
  - Follow-up:          follow_up from PrescriptionExtraction.

Plain-English condition prompt:
  system: "You are a patient-facing medical assistant. Explain the diagnosis in
           simple language a non-medical person can understand. Max 2 sentences.
           No jargon."
  user:   "Clinical assessment: {assessment}"

── BACKEND ──────────────────────────────────────────────────────────────────────

All analytics endpoints:
  - Protected by require_auth (from S8-0)
  - Accept doctor_id as query parameter
  - Read from Supabase via existing SQLAlchemy async engine

NOTE — Supabase free tier connection limits:
  Max 60 connections on free tier. The existing engine uses transaction pooler
  (port 6543) with statement_cache_size=0. Analytics queries are read-only and
  short-lived — no pooling changes needed.

GET /api/analytics/overview?doctor_id={id}
  Returns:
  {
    "total_sessions": 47,
    "sessions_today": 3,
    "sessions_this_week": 18,
    "avg_session_duration_minutes": 8.4,
    "notes_finalized_this_week": 12,
    "total_patients_seen": 43,
    "busiest_hour": 11,
    "finalized_notes_pct": 68.0
  }

  NOTE — confidence_score excluded from KPIs:
    It is an internal AI metric. A doctor seeing "72%" has no reference frame
    and it seeds doubt. It remains visible at session level in NoteReview only.

GET /api/analytics/icd-breakdown?doctor_id={id}&limit=10
  Use SQLAlchemy text() with jsonb_array_elements for the JSONB icd_codes array:

    SELECT
      elem->>'code'        AS code,
      elem->>'description' AS description,
      COUNT(*)             AS count
    FROM clinical_notes,
         jsonb_array_elements(icd_codes) AS elem
    WHERE session_id IN (
      SELECT id FROM sessions WHERE doctor_id = :doctor_id
    )
    GROUP BY code, description
    ORDER BY count DESC
    LIMIT :limit

  Return [] if no data — frontend handles empty state.

GET /api/analytics/sessions-by-day?doctor_id={id}&days=30
  Include days with zero sessions as {"date": "...", "count": 0} entries
  so the chart renders a continuous x-axis.

WHAT THIS SPRINT DOES NOT INCLUDE (intentionally deferred)
===========================================================

  1. Full authentication (JWT user accounts, clinic registration, multi-tenancy)
     Sprint 8 delivers a PIN gate (S8-0) sufficient for design partner pilots.
     Full auth with per-doctor login, clinic isolation, and role management
     is Sprint 9's primary focus.

  2. Patient identity / returning patient brief
     The Patient model and patient_id FK on sessions exist in DB schema.
     Wiring full patient search/create + pre-session history brief is its own
     sprint. Patient identity must come before referral letters.

  3. Referral letter generator
     Requires UX to capture referring specialist + clinical reason — additional
     form input not in current session flow. Content generation is straightforward
     (same LLM pattern) but data capture UX needs its own design pass.

  4. WhatsApp follow-up reminders
     Requires Meta Business API approval (2–6 weeks). Not a sprint item —
     a business/partnership track to run in parallel.

  5. Live differential diagnosis sidebar
     Regulatory/NMC liability exposure in India. Needs legal review first.
     Flagged for Sprint 10+ discussion.
